### Executed evaluator report

**Alignment summary.** This is a front door in the sense the brief means: ENS is the directory, the
router holds no roster, the model may only name an agent that discovery actually found, and the
answer a client reads carries the ENS name of the helper that produced it. The three wrong shapes
the evaluator names are each structurally excluded rather than merely avoided by good practice.

**The three named wrong shapes**

1. *One LLM answering everything and labelling the result with an agent's name.* Excluded by
   construction. `src/server/forward.ts` fetches `agent.endpoint` and nothing else — no map, no
   environment lookup, no model-supplied URL — and the attribution shown to the client is the ENS
   name of the agent that actually answered. The record run is the proof: six of eight cases came
   back with an answer produced by the downstream helper, and each took 1.2–1.3 s of real
   round-trip, not a single model call.
2. *Agents discovered from ENS but routed by brittle keyword matching.* Excluded.
   `src/server/route.ts` calls `decideRoute()` (`src/server/llm.ts`) and contains no keyword
   table, no `includes()` scoring and no heuristic fallback anywhere in the routing path. The two
   `no agent` cases prove the model is allowed to decline rather than being forced into the
   nearest lexical neighbour.
3. *A developer console where the client picks the agent from a dropdown.* Excluded.
   `src/web/App.tsx` has no agent `<select>`; the only picker is a list of recorded cases for
   trying the router, and the answer panel renders an attribution block ("Answered by" +
   ENS name).

**What's genuinely strong**

- **Criterion 1 is a named, isolated function with an explicit refusal.**
  `verifyRoutingDecision({ decision, discovered, model })` in
  `src/shared/routing-decision.ts`, called at `route.ts:216` before any forward. Its header
  states there is *no fallback agent anywhere in this file or its callers*, and an unknown name
  yields `'rejected-unknown-agent'`.
- **Criterion 3 is enforced by a test that greps the router's own source.**
  `src/server/no-literal-list.test.ts` (29 tests) walks the router files, fails on any literal
  ENS name (line 85) or endpoint (line 96), and separately asserts the configuration schema offers
  no way to list agents at all (line 100). A fourth agent cannot be added by editing router code,
  because a test forbids the shape that would require it.
- **Criterion 6 re-checks the endpoint at the last possible moment.**
  `forward.ts:92-98` calls `checkEndpointPolicy(agent.endpoint, { allowInsecureLocal })` again
  immediately before the request and refuses on failure, with a comment explaining that upstream
  validation is only a defence in depth. Criterion 5 sits in the same block:
  `AbortController` + `setTimeout` at `forward.ts:106-107`.
- **Criterion 4 degrades per-agent, not per-run.** `discovery.ts:154-158` `catch { continue }`
  inside the per-name loop, and `:353` notes a malformed record fails only its own strategy while
  the other discovery strategy still runs. The probe output shows the real version of this:
  `ens-registry empty` and `ens-subgraph failed` in the same run, with discovery still returning
  three agents.
- **The record format is adoptable, which is what the criterion rewards.**
  `docs/agent-record-format.md` plus `com.ensagent.*` service-key namespacing, and each record
  carries all three things the brief asks for: what it does (`capability`), how to reach it
  (`endpoint`), what it accepts (`accepts`). The probe prints all three per agent.
- **The agents are genuinely distinct specialists**, not three copies of one prompt: invoice
  (overdue balances, dunning, late fees), contract (termination, IP, liability, renewal clauses),
  brand copy (taglines, About pages, product descriptions) — each a separate process on its own
  port with its own records.

**Gaps & risks**

1. **No live ENS agents, so criterion 3's discovery half is not demonstrated end-to-end.**
   `probe:registry` reports `ens-registry=empty` for
   `replace-with-your-discovery-root-name.eth` (no `com.ensagent.registry.agents` record) and
   `ens-subgraph=failed`, then falls back to `dev-registry/registry.json`. The brief's step1 —
   publish each agent under an ENS name on Sepolia — is **NOT MET / BLOCKED BY ENS SETUP**. Note
   the *code* satisfies criterion 3 (runtime discovery, no literal list); what is missing is a
   published root to discover from.
2. **The `ens-subgraph` strategy fails on the placeholder root**, and the failure is a GraphQL
   argument error rather than an empty result. Harmless today because discovery is attempted
   first and the fallback is labelled, but it means the subgraph path has never been exercised
   against a real published parent name.
3. **`npm run record` needs a model endpoint that the repo does not ship.** `.env.example` is
   placeholders by design, so out of the box the script returns 0 of 8. A user who has not
   configured a provider sees a failing run with no hint that the cause is configuration. The
   script now exits non-zero (see below), which is honest, but the failure is still unlabelled.
4. **`npm run record` bootstraps nothing.** It does not start the three agents, so a first-time
   user following the README will get eight forward timeouts unless they start `npm run agents`
   first. The script's own banner does not say so. This cost this session one misdiagnosis.
5. **The two discovery sources have not been compared under real conditions**, so the
   `AGENT_DISCOVERY_SOURCES` default is untested against mainnet-shaped data volumes.

### Defects found and fixed in this run

**1. `scripts/record-routes.ts` reported success on a total failure.** `npm run record` returned
exit **0** with 0 of 8 cases matched, every case errored. A verification script that cannot fail is
not a check, and this one would have let a broken configuration pass unnoticed in CI. Now returns
1 on any mismatch and says so on stdout. Verified: exit 1 before the model was configured, exit 0
after.

**2. The generated doc claimed live ENS discovery from a run that discovered nothing.**
`render()` computed `usedDev = observations.some(o => o.attributionSource === 'dev-registry')`
and rendered `'Agents were discovered from live ENS records.'` in the `else` branch. When *every*
case errored, every `attributionSource` was `null`, so `usedDev` was `false` and the script
asserted the exact opposite of the truth — in a **tracked file** (`docs/routing-cases.md`). Provenance
is a three-way fact (live / labelled fallback / nothing attributed), not a boolean; it is now
computed as one, with an explicit "this run discovered nothing" case. Verified in the regenerated
doc: *"6 of 8 cases were answered by an agent from the labelled development fallback, not from ENS."*

**3. The doc printed the wrong discovery root.** The line read
`ROUTING_CASES.discoveryRoot` — the *expectations* dataset's root — not the root the run actually
queried, so the generated evidence could describe a name that was never read. It now prints
`config.agentDiscoveryRoot` and surfaces the dataset's root alongside it for comparison, which is
how the mismatch became visible.
